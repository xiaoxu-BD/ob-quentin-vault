# 保险承保工作内容与项目技术依据映射



当前工作内容可以表述为：

> 负责保险承保系统核心模块开发，围绕投保流程中的报价、核保、出单、收费、生效等关键节点，抽象产品、风险及投保主体三大核心模型；实现产品规则校验、风险评估、承保费用计算及共保费用分摊逻辑，并通过责任链、策略模式、状态机及异步消息机制解耦复杂校验与状态流转流程，提升承保链路的扩展性与一致性。

这段表述在本项目中可以找到比较自然的技术依据，但要注意：本项目本身是数藏交易系统，不是保险系统，因此更适合说“技术方案可类比/迁移”，不要直接声称项目里已有保险产品、共保、核保模型。

## 可作为依据的项目技术点

| 保险承保场景 | 项目中可对应的技术依据 | 合理表达方式 |
| --- | --- | --- |
| 投保流程：报价、核保、出单、收费、生效 | 交易链路中的预订、下单、支付、订单确认、订单完成 | 可以类比为“多阶段业务流程编排”，不要说项目已有保险投保流程 |
| 产品模型 | 商品/藏品/盲盒模型，如 `goods`、`collection`、`box` 模块 | 可对应保险产品定义、产品状态、价格/规则配置 |
| 风险模型 | 商品可售状态、库存、限流、用户认证、链路一致性校验 | 可对应承保风险评估、准入规则、业务风控校验 |
| 投保主体模型 | 用户模块、登录认证、实名/状态校验 | 可对应投保人、被保人、受益人等主体校验 |
| 产品规则校验 | `OrderCreateValidator` 责任链，包括用户、商品、预约、库存校验 | 可直接作为“责任链解耦承保校验”的依据 |
| 风险评估 | `UserValidator`、`GoodsValidator`、`StockValidator`、Sentinel 限流 | 可表达为“基于用户状态、产品状态、库存/额度及访问风险进行综合校验” |
| 出单状态流转 | `OrderStateMachine` 订单状态机 | 可对应保单从待核保、待收费、已收费、已生效、关闭等状态流转 |
| 收费与对账 | `pay` 模块、微信支付、支付单状态、支付对账任务 | 可对应保费收取、支付结果确认、账单一致性校验 |
| 生效与异步推进 | RocketMQ 事务消息、延迟消息、XXL-JOB 补偿任务 | 可对应支付成功后异步承保、生效、补偿重试 |
| 共保费用分摊 | 项目没有直接的共保模型，但存在金额计算、支付订单、对账、分布式一致性能力 | 建议说“基于金额计算与支付一致性经验实现共保费用分摊”，不要把它说成项目原生功能 |
| 高并发承保/批量投保 | Sentinel、Redis 库存扣减、RocketMQ 事务消息、分布式锁 | 可对应高并发投保、重复提交、幂等和一致性保障 |

## 关键代码依据

### 责任链校验

项目中存在完整的订单创建校验责任链：

- `OrderCreateValidator`：定义 `setNext`、`getNext`、`validate`。
- `BaseOrderCreateValidator`：实现模板逻辑，先执行当前校验，再调用下一个校验器。
- `UserValidator`：校验用户角色、状态、认证信息。
- `GoodsValidator`：校验商品状态和价格是否变化。
- `StockValidator`：校验库存是否充足。
- `OrderClientConfiguration`：将校验器组装为链路。

可迁移到保险承保系统的表达：

> 将投保准入、产品规则、主体身份、风险因子、额度限制、费用规则等校验拆分为独立校验器，并通过责任链按产品线动态编排，避免核保流程中大量 `if-else` 堆叠。

### 策略模式/工厂模式

项目中通过工厂按类型选择具体服务实现：

- `ChainServiceFactory`：根据 `ChainType` 选择不同上链服务。
- `BlindBoxRuleServiceFactory`：根据盲盒分配规则选择不同分配策略。
- `PayChannelServiceFactory`：根据支付渠道选择不同支付服务。

可迁移到保险承保系统的表达：

> 将不同险种、不同核保规则、不同费用分摊规则抽象为策略接口，由工厂根据产品编码、渠道、共保方案或风险类型选择对应策略，降低新增产品规则时对主流程的影响。

### 状态机

项目中 `OrderStateMachine` 管理订单状态变化，例如：

- `CREATE -> CONFIRM`
- `CONFIRM -> PAID`
- `CONFIRM -> CLOSED`
- `PAID -> FINISH`

可迁移到保险承保系统的表达：

> 使用状态机约束投保单/保单状态流转，保证报价、核保、出单、收费、生效、退回、关闭等节点只能按合法事件推进，降低状态错乱风险。

### 分布式一致性

项目中有多种一致性方案：

- RocketMQ 事务消息：库存预扣、订单创建、本地事务反查。
- TCC：`TradeApplicationService` 中存在 Try/Confirm/Cancel 方案。
- 分布式锁：`@DistributeLock` 防止重复下单。
- 延迟消息与补偿：下单失败、确认失败后通过延迟消息进行补偿。
- 支付对账：`PayDetailCheckJob` 对支付订单和渠道流水做金额、状态核对。

可迁移到保险承保系统的表达：

> 针对投保、出单、收费、生效跨模块链路，引入事务消息、幂等键、分布式锁和定时对账补偿机制，保障保单状态、收费状态和业务流水最终一致。

## 与保险业务的合理映射

### 产品、风险、主体三大模型

可以这样设计并描述：

- 产品模型：维护险种、计划、保障责任、费率因子、承保规则、缴费方式、生效规则。
- 风险模型：维护风险标的、风险因子、风险等级、核保结论、拒保/加费/转人工规则。
- 主体模型：维护投保人、被保人、受益人、企业客户、证件、关系、实名状态。

对应项目依据：

- 商品/藏品模型对应“产品可售性、价格、状态、规则”。
- 用户模型对应“主体状态、认证、准入”。
- 库存/限流/一致性校验对应“额度、风险阈值、并发准入”。

### 共保费用分摊

共保费用分摊在项目里没有直接业务实现，但可以基于项目已有的金额与支付能力做合理延伸：

- 使用 `BigDecimal` 做金额计算，避免精度问题。
- 基于主承保方、共保方、分摊比例、保费、手续费、税费生成分摊明细。
- 通过唯一业务号保证分摊结果幂等。
- 收费成功后异步推进分摊流水状态。
- 定时任务对支付金额、分摊金额、保单金额做一致性核对。

建议描述为：

> 负责实现共保费用分摊逻辑，基于保单保费、共保比例及费用项生成分摊明细，使用 `BigDecimal` 保证金额精度，并通过幂等流水号、事务消息和定时对账任务保障收费结果与分摊结果最终一致。

## 可用于简历/述职的版本

### 简洁版

负责保险承保系统核心模块开发，围绕报价、核保、出单、收费、生效等投保主流程，抽象产品、风险及投保主体三大核心模型；基于责任链模式拆分产品规则、主体准入、风险因子及额度校验逻辑，基于策略模式支持不同险种和共保方案的费用计算与分摊；结合状态机、事务消息、分布式锁和定时对账机制，保障保单状态、收费状态及费用流水的一致性。

### 技术强化版

负责承保核心链路设计与开发，参与投保单、保单、产品规则、风险因子、主体信息等领域模型抽象；使用责任链模式将主体校验、产品规则校验、风险评估、额度校验等逻辑解耦为可插拔节点，支持按险种和渠道动态编排；使用策略模式实现不同产品的报价规则、核保规则及共保费用分摊算法；通过状态机约束报价、核保、出单、收费、生效、关闭等状态流转，并结合 RocketMQ 事务消息、Redis 幂等控制、分布式锁和 XXL-JOB 对账补偿，保障跨模块业务链路最终一致。

### 面试展开版

项目中承保链路涉及多个强状态节点：报价后需要进入核保，核保通过后才能出单，收费成功后再推进保单生效。为了避免规则逻辑堆在主流程中，我将承保校验拆成多个责任链节点，例如主体资质校验、产品规则校验、风险因子校验、额度校验和费用校验；不同险种之间差异较大的报价、核保和共保分摊逻辑则通过策略接口承载，由工厂根据产品编码和业务场景选择具体实现。收费和生效环节涉及支付状态、保单状态、费用分摊流水的跨模块一致性，因此使用事务消息、幂等键、分布式锁和定时对账任务进行兜底，保证主流程高并发下不会出现重复出单、重复收费或状态不一致。

## 面试时可以主动说明的边界

为了显得真实，建议主动把边界说清楚：

- 责任链主要用于承保前置校验，不把所有业务逻辑都塞进责任链。
- 策略模式主要用于差异化规则，例如不同险种报价、不同核保规则、不同共保分摊方案。
- 状态机负责状态合法性，不负责复杂业务决策。
- 事务消息和定时任务解决的是最终一致性，不等价于强一致事务。
- 共保费用分摊的难点不是公式本身，而是金额精度、舍入规则、幂等、支付成功后的状态推进和对账。

## 不建议使用的夸张说法

- 不建议说“完全自研保险核心系统”，除非确实覆盖了全流程生产能力。
- 不建议说“强一致保证所有承保链路”，跨服务场景通常更合理的是最终一致。
- 不建议说“规则引擎”，除非实际使用了 Drools、QLExpress、Aviator 或自研 DSL。
- 不建议说“共保清结算系统”，如果你只做了承保侧分摊明细，应该说“共保费用分摊与收费一致性处理”。
- 不建议把本项目的数藏、库存、上链业务直接替换成保险业务，应强调“技术方案迁移”。
