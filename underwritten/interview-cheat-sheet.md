## 二、技术场景详解（7 大场景）

### 场景 1：投保流程开发（多阶段业务流程）

#### 业务概述

投保流程包含多个节点：报价 → 核保 → 出单 → 收费 → 生效。每个节点都需要参数校验、状态判断、失败返回和后续流程推进。

#### 对应项目技术依据

| 保险承保 | 项目对应              | 说明                 |
| ---- | ----------------- | ------------------ |
| 报价   | `/book` 预订接口      | 提交信息，系统初步计算        |
| 核保   | 下单校验流程            | 产品规则 + 主体 + 风险综合判断 |
| 出单   | 订单确认              | 校验通过，生成正式单据        |
| 收费   | `/pay` 支付接口       | 创建支付单，等待支付回调       |
| 生效   | `paySuccess` 回调处理 | 支付成功后推进订单状态        |

项目中 `TradeController` 存在 `/book`、`/buy`、`/normalBuy`、`/pay`、`/cancel` 等接口，交易链路包含预订、下单、支付、取消、完成等多阶段流程。

#### 简历描述

> 参与投保主流程接口开发，负责报价、核保、出单、收费、生效等节点的业务逻辑实现，处理投保单基础信息、产品信息、风险信息及主体信息的参数校验和状态推进。

#### 面试展开

> 我主要参与承保链路中的接口开发和业务逻辑实现。比如用户提交投保信息后，系统会先做产品规则和主体信息校验，再根据风险信息进行核保判断，通过后生成投保单或保单，收费成功后再推进到生效状态。我的工作重点是把每个节点需要的参数校验、状态判断和异常返回处理清楚，保证流程能按业务规则往下走。

### 场景 2：产品规则校验

#### 业务概述

根据产品配置校验投保年龄、保障期限、缴费方式、起保时间、保额范围等规则，不符合产品要求的请求不允许进入后续核保流程。

#### 对应项目技术依据

- `GoodsValidator`：校验商品状态、价格是否变化。
- 商品/藏品模型可类比保险产品模型（产品可售性、价格、状态、规则）。
- 校验逻辑从主流程中拆出，避免控制器或服务方法堆积大量判断。

#### 简历描述

> 实现产品规则校验逻辑，支持对险种状态、保障期限、缴费方式、保额范围、起保时间等规则进行校验，并将校验失败原因按统一错误码返回，提升投保流程异常提示的准确性。

#### 面试展开

> 产品规则校验是投保流程的第一道关。不同险种有不同的投保年龄范围、保障期限、保额上下限、缴费方式限制等。如果把这些规则全部写在一个方法里，新增产品时改动量很大。我们的做法是把每类规则做成独立的校验节点，失败直接返回统一格式的错误信息，方便前端展示具体哪一项不符合要求。

### 场景 3：投保主体校验

#### 业务概述

对投保人、被保人、受益人等主体信息进行基础校验，包括证件类型、证件号、手机号、年龄、关系、实名状态等。

#### 对应项目技术依据

- `UserValidator`：校验用户角色、状态、认证信息。
- `AuthController`：用户注册、登录、验证码校验。
- 保险主体校验和用户准入校验在技术实现上都属于主体资格判断。

#### 简历描述

> 参与投保主体信息校验功能开发，对投保人、被保人、受益人的证件信息、联系方式、年龄范围、人员关系及实名状态进行校验，减少无效投保请求流入核保环节。

#### 面试展开

> 主体校验主要是确认投保人、被保人、受益人这些人的信息是否合法。比如投保人必须是成年人，被保人年龄要在产品允许范围内，受益人和被保人要有合法关系，证件号要通过格式校验，手机号要能接收验证码。这些校验在进入核保之前就要做完，避免无效请求占用后续资源。

### 场景 4：风险信息校验与风险评估

#### 业务概述

根据险种要求对职业类别、健康告知、地区、保额上限、历史投保记录等风险因子进行基础校验，返回通过、拒绝或转人工核保等结果。

#### 对应项目技术依据

- `StockValidator`：根据库存判断是否允许继续下单。
- Sentinel：对热点接口做限流保护。
- 项目中的库存、限流、状态校验可类比承保中的额度、风险阈值、准入控制。

#### 适合 1-2 年的说法

> 我主要负责风险信息的规则校验和结果处理，不主导复杂风控模型。比如根据产品配置判断职业类别是否可投、保额是否超过限制、健康告知是否触发人工核保，并将核保结果返回给后续出单流程。

#### 面试展开

> 风险校验不是一个复杂模型，更多是基于规则的判断。比如某些高危职业可能不在投保范围内，保额超过一定限额需要转人工核保，某些地区因为灾害风险可能限制投保。我负责的是把产品配置的规则读出来，和用户提交的信息做比对，返回核保结论：自动通过、自动拒绝、或转人工。

### 场景 5：责任链模式拆分校验流程 ⭐ 核心重点

#### 业务概述

将产品规则校验、主体信息校验、风险信息校验、费用校验等逻辑拆分为多个独立校验节点，按业务顺序依次执行。

#### 对应项目技术依据

| 项目代码 | 职责 |
|---|---|
| `OrderCreateValidator` | 定义责任链接口：`validate` + `setNext` + `getNext` |
| `BaseOrderCreateValidator` | 模板方法：执行当前校验，通过后调用下一个节点 |
| `UserValidator` | 校验用户角色、状态、认证信息 |
| `GoodsValidator` | 校验商品状态和价格是否变化 |
| `StockValidator` | 校验库存是否充足 |
| `OrderClientConfiguration` | 将校验器组装为完整链路 |

#### 核心代码逻辑（面试可画在白板上）

```
接口：OrderCreateValidator
  ├─ validate(request)  → 执行当前节点校验
  ├─ setNext(validator) → 设置下一个校验器
  └─ getNext()          → 获取下一个校验器

实现类：
  BaseOrderCreateValidator
    └─ 执行 validate 时：先调自身校验逻辑，通过后调 getNext().validate()

具体节点：
  UserValidator    → 用户状态、认证
  GoodsValidator   → 商品状态、价格
  StockValidator   → 库存是否充足

组装（Spring 配置或代码组装）：
  UserValidator → GoodsValidator → StockValidator
```

#### 简历描述

> 使用责任链模式重构投保校验流程，将产品规则、主体资质、风险信息、费用规则等校验拆分为独立节点，减少主流程中的条件分支，提升后续新增校验规则的便利性。

#### 面试详细展开（这是重点，准备充分）

**面试官：你为什么用责任链？**

> 承保校验规则比较多，比如产品规则、主体资质、风险信息、费用规则等。如果全部写在一个 service 方法里，会有很多条件分支，后续新增规则也容易影响原有逻辑。责任链可以把每类校验拆成独立节点，每个节点只关注自己的规则，校验失败就中断并返回明确错误，校验通过再进入下一个节点。

**面试官：能具体说下代码怎么组织的吗？**

> 我们定义了一个统一的校验接口，包含 `validate` 和 `setNext` 方法。有一个基类实现了模板逻辑：执行当前节点的校验，通过后自动调用下一个节点的 `validate`。具体的校验逻辑在各自的实现类里，比如产品校验器只管产品规则，主体校验器只管人员信息。最后通过配置类把这些校验器按业务顺序组装成一条链路。

**面试官：新增一个校验规则怎么办？**

> 只需要新增一个校验器实现类，写好自己的校验逻辑，然后在组装配置里把它加到链路中合适的位置就行。不需要改主流程代码，也不影响其他校验器。这也是责任链最大的好处 —— 开放扩展、对修改封闭。

**面试官：所有校验都走责任链吗？**

> 不是。责任链主要用于承保前置校验，就是那些"有一个不通过就不能往下走"的规则。像一些后置计算、结果组装这些逻辑，不需要放进责任链。我们只把校验性质的逻辑拆成链路，避免责任链变成万能管道。

### 场景 6：策略模式处理差异化规则 ⭐ 核心重点

#### 业务概述

不同险种、不同渠道、不同共保方案下，报价规则、核保规则、费用分摊规则可能完全不同。用策略模式封装差异，主流程只负责选择和调用。

#### 对应项目技术依据

| 工厂类 | 选择依据 | 选择对象 |
|---|---|---|
| `ChainServiceFactory` | `ChainType` 链类型 | 不同上链服务 |
| `BlindBoxRuleServiceFactory` | 盲盒分配规则 | 不同盲盒分配策略 |
| `PayChannelServiceFactory` | 支付渠道 | 不同支付服务实现 |

#### 核心代码逻辑

```
策略接口：XxxStrategy
  └─ execute(params) → 执行具体业务逻辑

具体策略：
  HealthInsuranceQuoteStrategy    → 健康险报价规则
  PropertyInsuranceQuoteStrategy  → 财产险报价规则
  AccidentInsuranceQuoteStrategy  → 意外险报价规则

工厂：QuoteStrategyFactory
  └─ getStrategy(productCode) → 根据产品编码返回对应策略

调用方（主流程）：
  strategy = factory.getStrategy(productCode)
  result = strategy.execute(params)
```

#### 简历描述

> 基于策略模式封装不同险种的费用计算和共保分摊逻辑，根据产品编码或分摊方案选择对应策略，降低新增产品规则时对原有流程的影响。

#### 面试详细展开

**面试官：策略模式用在哪里？**

> 主要用在差异化比较明显的地方，比如不同险种的保费计算规则、不同产品的核保规则、不同共保方案的费用分摊规则。主流程只负责拿到产品编码或分摊方案，然后通过工厂选择对应策略执行，避免在主流程里写大量 `if-else`。

**面试官：工厂是怎么选择策略的？**

> 项目里有几种做法。一种是通过枚举或编码做 key，从 Map 里取对应的策略实例，比如 `PayChannelServiceFactory` 根据支付渠道编码选择支付服务。另一种是 Spring 注入，策略实现类都实现了同一个接口，通过 `@Autowired` 注入一个 List，再根据业务类型过滤。具体用哪种取决于策略数量和变化频率。

**面试官：你做的策略模式和 if-else 有什么本质区别？**

> `if-else` 是把所有逻辑堆在一起，新增一个险种就要改主流程代码，容易引入 bug。策略模式把每个险种的逻辑独立封装，新增险种只需要加一个策略类和一行工厂注册，主流程完全不用动。这符合开闭原则 —— 对扩展开放，对修改关闭。

**面试官：什么情况下你不建议用策略模式？**

> 如果只有两三种情况，差异也不大，用 `if-else` 或 `switch` 反而更清晰。策略模式适合场景多、差异大、且经常新增的情况。保险里险种多、规则差异大，所以比较适合。

### 场景 7：状态流转控制

#### 业务概述

投保单/保单有严格的生命周期状态，每个操作只能在合法状态下执行。

#### 状态流转图（面试可画在白板上）

```
投保单状态流转：

待报价 → 待核保 → 核保通过 → 待收费 → 已收费 → 已生效 → [已关闭]
   ↓         ↓         ↓          ↓         ↓
 [拒绝]   [拒绝]   [退回修改]  [超时关闭] [退款关闭]

对应代码中的状态机：

CREATE → CONFIRM → PAID → FINISH
  ↓         ↓        ↓
CLOSED   CLOSED   CLOSED
```

#### 对应项目技术依据

- `OrderStateMachine` 管理订单从 `CREATE` → `CONFIRM` → `PAID` → `FINISH` / `CLOSED` 等状态流转。
- 每次状态变更前做前置校验，确认当前状态允许执行目标操作。

#### 简历描述

> 参与投保单状态流转逻辑开发，对核保、出单、收费、生效、关闭等操作增加状态前置校验，避免重复出单、重复收费及非法状态推进。

#### 面试展开

**面试官：状态流转你怎么控制的？**

> 我会把状态校验放在关键业务操作前面。比如收费前要确认投保单已经核保通过，生效前要确认已收费成功，关闭后不允许再继续推进。这样可以避免因为重复请求或异常回调导致状态错乱。

**面试官：为什么不用现成的状态机框架？**

> 我们用的是项目里已有的 `OrderStateMachine`，它通过配置定义了哪些状态可以转到哪些状态。每次操作前调用状态机的校验方法，如果不允许就直接抛异常。对于 1-2 年经验来说，我不主导框架选型，主要是基于现有状态机接入新的业务状态和流转规则。

**面试官：状态机和责任链有什么区别？**

> 责任链解决的是"多个校验规则如何组织"的问题，每个节点做的都是校验，有一个不通过就中断。状态机解决的是"哪些操作在当前状态下合法"的问题，它约束的是业务动作的执行条件。两者配合使用：状态机保证操作合法性，责任链保证业务数据合法性。

### 场景 8（附加）：收费回调与幂等控制

#### 业务概述

收费成功后要推进保单状态，同时必须处理重复回调、状态已更新、金额不一致等异常场景。

#### 对应项目技术依据

- `TradeController.pay` 创建支付单。
- `OrderFacadeServiceImpl.paySuccess` 处理支付成功后的订单状态推进。
- `PayDetailCheckJob` 支付对账任务，对支付订单和渠道流水做金额与状态核对。
- 分布式锁 `@DistributeLock` 防止重复下单。

#### 简历描述

> 参与收费结果回调处理，根据收费成功结果推进保单状态，并对重复回调、状态异常、金额不一致等场景进行基础校验和幂等处理。

#### 面试展开

**面试官：怎么保证重复回调不出问题？**

> 我们会使用业务唯一标识做幂等控制，比如投保单号、收费流水号或分摊批次号。处理前先判断当前状态和已有流水，如果已经处理成功就直接返回成功；如果状态不允许继续推进，就返回明确错误，避免重复出单、重复收费或重复生成分摊明细。

**面试官：幂等和分布式锁有什么区别？**

> 分布式锁是"同一时刻只有一个请求能进来"，适用于并发场景，比如防止重复下单。幂等是"同一个请求处理多次结果一致"，适用于回调场景，比如支付平台可能多次回调同一个支付结果。我们收费回调用的是幂等，因为支付回调不是并发问题，是重复通知问题。

### 场景 9（附加）：共保费用分摊

#### 业务概述

一张保单由多个共保方按比例承担保费时，需要生成分摊明细，处理金额精度、比例校验和尾差调整。

#### 关键技术点

- 金额必须用 `BigDecimal`，不能用 `float` 或 `double`。
- 分摊前校验共保比例合计是否为 100%。
- 分摊后校验各方金额合计是否等于总保费。
- 四舍五入产生的一分钱尾差，按业务规则补到主承保方或指定承保方。
- 通过唯一业务号保证分摊结果幂等。

#### 简历描述

> 参与共保费用分摊逻辑开发，基于保费金额、共保比例及费用项生成分摊明细，使用 `BigDecimal` 处理金额精度，并对比例合计、金额合计和尾差进行校验，保证分摊结果与保单金额一致。

#### 面试展开

**面试官：共保费用分摊有什么难点？**

> 难点主要是金额精度、比例校验和尾差处理。金额不能用浮点数，需要用 `BigDecimal`。分摊前要校验共保比例合计是否符合要求，分摊后要校验各方金额合计是否等于总保费。如果因为四舍五入出现尾差，需要按业务规则补到主承保方或指定承保方。比如一张保单总保费 100 元，三个共保方按 40%、35%、25% 分摊，计算结果可能是 40.00、35.00、25.00，刚好整除没问题；但如果总保费是 100.01，可能算出 40.004、35.0035、25.0025，四舍五入后变成 40.00、35.00、25.00，合计变成 100.00，差了一分钱，这一分钱要按规则补到指定承保方。

### 场景 10（附加）：异常补偿与定时任务

#### 业务概述

强流程业务必须考虑异常补偿。收费成功但保单未生效、状态长时间未推进、分摊明细异常等场景需要定时扫描和补偿。

#### 对应项目技术依据

- XXL-JOB 定时任务：支付对账 `PayDetailCheckJob`、订单超时、支付单检查。

#### 简历描述

> 参与承保链路异常补偿任务开发，通过定时任务扫描长时间未推进的投保单、收费单及分摊明细，并根据业务状态进行重试或异常标记，提升流程稳定性。

#### 面试展开

> 比如收费已经成功，但保单因为网络或服务异常没有及时生效，这种情况不能只靠用户再次操作。我们通过定时任务扫描收费成功但未生效的数据，再根据当前状态进行补偿推进或记录异常告警。另外对于一些异步处理失败的场景，会通过延迟消息做重试，重试超过一定次数后转人工处理。

## 三、高频面试 Q&A 汇总（共 15 题）

### 设计模式类

**Q1：你用过哪些设计模式？在什么场景下用的？**

> 项目中主要用了三种：责任链、策略/工厂、状态机。责任链用于拆分投保校验流程，把产品规则、主体资质、风险信息、费用规则拆成独立节点。策略模式用于不同险种的差异化规则，比如不同险种的报价规则和费用计算方式不同，通过工厂选择对应策略执行。状态机用于控制投保单和保单的状态流转，保证每个操作只能在合法状态下执行。

**Q2：为什么用责任链而不是 if-else？**

> `if-else` 在规则少的时候没问题，但承保校验规则很多，全部堆在一个方法里会有大量条件分支，后续新增规则容易影响原有逻辑。责任链每个节点只关注一类规则，新增规则只需要新增校验器并接入链路，不影响其他节点。符合开闭原则。

**Q3：责任链的性能会不会比 if-else 差？**

> 理论上责任链有对象创建和方法调用的开销，但在承保场景下，校验逻辑本身的业务开销远大于链路调用的开销。而且责任链带来的可维护性和可测试性收益远大于这点性能差异。如果真的对性能极度敏感，可以考虑把责任链的节点编译为一个有序列表，减少链式调用。

**Q4：策略模式和工厂模式是什么关系？**

> 策略模式定义了一系列可互换的算法或规则，工厂模式负责创建和选择具体策略。两者经常配合使用：工厂根据业务参数（产品编码、渠道类型）选择对应的策略实例，然后调用策略的执行方法。项目里的 `PayChannelServiceFactory` 就是典型的工厂 + 策略组合。

**Q5：状态机在项目中是怎么实现的？用了什么框架？**

> 用的是项目里已有的 `OrderStateMachine`，它通过配置定义了状态和事件的映射关系。每次操作前调用状态机校验当前状态是否允许执行目标操作。对于 1-2 年经验来说，我不主导框架选型，主要是基于现有状态机接入新的业务状态和流转规则。

### 业务逻辑类

**Q6：投保流程是怎样的？你能简单说一下吗？**

> 简单说就是五个节点：报价、核保、出单、收费、生效。用户提交投保信息后，系统先做产品规则和主体信息校验，再根据风险信息做核保判断，通过后生成投保单，然后进入收费环节，收费成功后保单生效。每个节点都有状态校验，不合法的状态不允许往下推进。

**Q7：产品规则校验具体校验什么？**

> 主要校验投保年龄是否在产品允许范围内、保障期限是否符合产品定义、缴费方式是否支持、保额是否在上下限内、起保时间是否合法等。这些规则从产品配置中读取，和用户提交的信息做比对，不符合就返回具体哪个字段不符合要求。

**Q8：风险校验和产品校验有什么区别？**

> 产品校验是看"这个产品能不能卖给你"，比如年龄不符合、保额超限。风险校验是看"你这个人适不适合保"，比如职业类别是否高危、健康告知是否有异常、投保地区是否有特殊风险。产品校验是硬规则，不通过就不行；风险校验可能有三种结果：自动通过、自动拒绝、转人工核保。

### 技术实现类

**Q9：怎么处理重复提交？**

> 两层防护。第一层是前端防抖和按钮禁用。第二层是后端幂等，用业务唯一标识（比如投保单号）做幂等判断。创建投保单时先查是否已有相同标识的记录，有就直接返回已有结果。收费回调也一样，用收费流水号做幂等。

**Q10：分布式锁和幂等有什么区别？分别用在什么场景？**

> 分布式锁解决的是并发问题，同一时刻只有一个请求能执行，适合防止重复下单。幂等解决的是重复请求问题，同一个请求处理多次结果一致，适合支付回调场景。分布式锁用 `Redis` + `@DistributeLock` 实现，幂等用业务唯一标识 + 状态校验实现。

**Q11：金额计算为什么不能用 double？**

> `double` 是浮点数，存在精度丢失问题。比如 `0.1 + 0.2` 不等于 `0.3`，在金融场景下这是致命的。必须用 `BigDecimal`，它基于定点数运算，不会丢失精度。创建 `BigDecimal` 时要用字符串构造器 `new BigDecimal("0.1")`，不能用 `new BigDecimal(0.1)`，后者同样会有精度问题。

**Q12：共保费用分摊的尾差怎么处理？**

> 先按比例计算各方分摊金额，再用 `BigDecimal` 的 `setScale` 控制小数位数。计算完后校验各方金额合计是否等于总保费。如果差一分钱，按业务规则把尾差补到主承保方或指定承保方，保证明细合计和总保费完全一致。

### 系统设计类

**Q13：你们怎么保证收费后保单一定生效？**

> 收费成功后，主流程会尝试推进保单状态到生效。但如果因为网络抖动或服务异常导致生效失败，我们有补偿机制：定时任务扫描收费成功但未生效的保单，进行重试推进。重试超过一定次数后转人工处理并告警。这是最终一致性的思路，不是强一致。

**Q14：异常补偿怎么做的？**

> 主要有两种方式。一种是定时任务，比如 XXL-JOB 定时扫描长时间未推进的投保单、收费成功但未生效的保单，根据当前状态做重试或标记异常。另一种是延迟消息，比如下单失败后发一个延迟消息，延迟一段时间后再检查状态做补偿。

**Q15：你在这个项目中遇到的最大技术挑战是什么？**

> 我觉得比较有挑战的是校验逻辑的组织方式。承保校验规则多且变化频繁，如果全写在一个方法里，后期很难维护。我参与的工作是把校验逻辑通过责任链拆分成独立节点，这样新增规则时只需要新增一个校验器，不需要改主流程代码。虽然这不是架构层面的设计，但在具体功能开发中，如何把规则拆得合理、让每个节点职责清晰，还是需要一些思考的。
