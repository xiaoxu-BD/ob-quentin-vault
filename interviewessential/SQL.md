```plain
查询2023年每个VIP等级用户的平均订单金额（只计算已支付订单），
并按VIP等级升序排列。如果某个VIP等级没有用户，则不需要显示该等级

分析条件: 
1. 要2023年的数据 使用year(year_time) 匹配2023
2. 每一个vip等级用户: 涉及到分组
3. 计算已支付的订单 where 条件过滤
4. 排序
```

```plsql

SELECT 
    u.vip_level,
    AVG(o.total_amount) AS avg_order_amount
FROM 
    users u
JOIN 
    orders o ON u.user_id = o.user_id
WHERE 
    o.status = 'paid'
    AND YEAR(o.order_date) = 2023
GROUP BY 
    u.vip_level
ORDER BY 
    u.vip_level ASC;

```

```plain
找出那些购买了"电子产品"类别商品，但从未购买过"服装"类别商品的用户。
要求返回这些用户的用户名、邮箱和注册日期，并按注册日期降序排列


-- 
分析购买了电子产品类别商品 但是(重点) 从未购买过服装的商品
要用in  not in 
```

```plsql
SELECT 
    u.username, 
    u.email, 
    u.register_date
FROM 
    users u
WHERE 
    u.user_id IN (
      -- 购买了电子产品的用户
      SELECT DISTINCT o.user_id
      FROM orders o
      JOIN order_items oi ON o.order_id = oi.order_id
      JOIN products p ON oi.product_id = p.product_id
      WHERE p.category = '电子产品'
    )
    AND u.user_id NOT IN (
      -- 从未购买过服装的用户
      SELECT DISTINCT o.user_id
      FROM orders o
      JOIN order_items oi ON o.order_id = oi.order_id
      JOIN products p ON oi.product_id = p.product_id
      WHERE p.category = '服装'
    )
ORDER BY 
    u.register_date DESC;
```

## 主从复制和集群的区别
Master 多个Slave 一主多从

---

## 1️⃣ 主从复制（Replication）
+ **核心思想**：一个库作为主库（Master），把自己的 **binlog（二进制日志）** 传给从库（Slave），从库重放日志，保持数据一致。
+ **特点**：
    - **架构**：1 主 N 从（通常是单主写入、多从读取）。
    - **同步方式**：异步 / 半同步。
    - **作用**：
        * 分担读压力（读写分离：主写，从读）。
        * 备份冗余（从库可作为灾备）。
    - **问题**：
        * 主库宕机后需要人工切换。
        * 数据延迟可能比较大（从库滞后）。
        * 一般不保证强一致性。

👉 **适合：中小型业务，重点是读性能提升。**

---

## 2️⃣ MySQL Cluster（MGR 或 NDB Cluster）
⚠️ 这里的 “MySQL Cluster” 指的是官方的 **高可用集群方案**，分两类：

### （1）MySQL Group Replication (MGR)
+ **核心思想**：基于分布式一致性协议（类 Paxos/Raft），多个节点之间 **强一致**。
+ **特点**：
    - **架构**：多主写入（Multi-Primary） 或 单主写入（Single-Primary）。
    - **自动故障转移**：节点挂掉，自动选举新的主库。
    - **数据一致性**：事务提交时，必须得到多数节点确认，保证 **强一致性**。
    - **运维简单**：配合 MySQL Router，可以自动路由 SQL。

👉 **适合：对可用性、一致性要求很高的场景。**

### （2）MySQL NDB Cluster（比较少用）
+ **存储引擎 NDB**，数据分片 + 多副本，属于分布式数据库。
+ 高吞吐、低延迟，但兼容性比 InnoDB 差。
+ 主要用在电信级场景。

---

## 3️⃣ 总结对比
| 对比项 | 主从复制 | MySQL Cluster (MGR) |
| --- | --- | --- |
| 架构 | 1 主 N 从 | 多主或单主，强一致集群 |
| 写入能力 | 只有主库能写 | 多主写入（可选） |
| 数据一致性 | 弱一致（有延迟） | 强一致（提交需多数确认） |
| 故障转移 | 手动切换 | 自动故障转移 |
| 部署复杂度 | 简单 | 相对复杂 |
| 适用场景 | 读多写少，读写分离 | 高可用、强一致、金融级业务 |


---

📌 **一句话概括：**

+ **主从复制**：便宜、简单，用来分担读压力。
+ **MySQL 集群（MGR）**：贵、复杂，用来保证 **高可用 + 强一致性**。
